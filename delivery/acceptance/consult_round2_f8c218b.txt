2. CORE CORRECTNESS

Durability: successful backup publication does not fix the existing-blob capture path

Revising F14: the post-commit attachment response handling is substantially repaired. The handler now preserves a committed original receipt when subsequent extraction fails, and the new tests deliberately inject post-commit failures. That is a genuine improvement over falsely saying nothing was saved.

However, I found a separate foreground durability defect in _write_blob. Its file synchronization and directory synchronization occur only inside if not blob.exists(). Consider this sequence:

An upload writes and synchronizes the temporary file, renames it to its content-addressed name, and then directory synchronization fails.

The call returns storage_unavailable, but the renamed blob remains.

The same upload is retried. Because the blob exists, the retry skips synchronization, verifies its readable hash, and proceeds to the database mutation and committed receipt.

The missing durability barrier has not been retried. A concurrent identical upload can take the same shortcut after another writer’s rename but before that writer’s directory synchronization. Readable bytes and a matching hash do not establish the directory-publication ordering promised by the capture contract. I am not claiming your existing originals have disappeared; I am identifying a supported path that acknowledges them without establishing that ordering.

The small fix is to ensure the verified blob and its directory are successfully synchronized before permitting a new database reference, including the existing-file branch. The discriminating test is a persistent directory-sync failure: the first attempt and same-byte retry must both fail without a receipt; removing the fault must then allow one committed capture.

Migration v6 and retirement: attribution is improved, publication remains unsafe

Revising F01: boundary-shrink detection, affected-group rebuilding, indexed latest-sample recomputation, and the randomized SQL-oracle test address the original catalog defect. The property test compares maintenance results with independent aggregation after mutations, rather than merely asserting a successful import. I count that specific finding as cleared at the code/test level.

The export_legacy_owner rule is conservative under its necessary assumption: import_runs is the complete history of imports that created those untagged rows. V6 assigns an owner only when the distinct archive-hash set has one member. _retire requires that owner for untagged rows, or a matching export tag and older parser version for tagged rows. A later, different export’s tagged rows do not satisfy that predicate merely because the legacy owner exists. Failed or repeated imports of other archive hashes make attribution more conservative, not more aggressive. I did not find a straightforward serialized-import counterexample that makes this owner predicate select an unrelated tagged export.

That is not an unconditional retirement guarantee, for two reasons.

First, eligibility checking and retirement are separate transactions. _retire selects native IDs, closes the connection, and later sends deletion-only batches. Those deletions do not recheck the selected row’s export attribution, parser version, or observation version. If another import updates a selected identity between selection and deletion—for example a shared day-summary identity—the retirement can delete its replacement. This is a concurrency hole, not a defect in the Boolean owner predicate. Serialize import generations or revalidate eligibility inside the mutation transaction. Test the actual interleaving, not only two sequential imports.

Second, the archive exposes both generations while replacement is underway. New x2: rows are committed page by page; old rows remain canonical until _retire, which itself runs page by page. The supersession table does not suppress old-parser backfill rows in favor of new-parser backfill rows. Foreground queries can therefore see old-plus-new contributions during import, and an interrupted import can leave that overlap in place. Recording a failed import internally does not protect ChatGPT when its readable source status and query tools do not expose an analytical maintenance gate.

This matters immediately because your context says the production re-import is running. The reported final reconciliation on the rehearsal copy does not establish coherent queries during that operation.

For the current deployment, the smallest fix is a durable import-maintenance state that blocks affected observation analyses until reconciliation succeeds, while allowing unrelated text capture. A staged generation with an atomic publication switch is the better permanent implementation.

--since is substantially improved: filtering uses normalized instants, naive/date-only inputs use the selected user timezone, and import options contribute to request identity. The existing partial-import tests are useful. But passing those tests does not prove all older rows selected for retirement received valid replacements: parsing can increment unparseable and continue, after which retirement still executes. Retirement should fail closed on unresolved replacement gaps, and its window tests should include legacy timestamps whose projection changes under the new parser—not just identical old/new instant representations.

Canonicalization: stable-key arrival ordering is fixed, identity ambiguity is not

Revising F02/F03: for a stable equivalence key, the supersession relation fixes the original arrival-order defect and retains deletion authority. Export-first and live-first produce the intended suppression, and tombstoned live rows are included when rebuilding the relation. The permutation and migration tests exercise real regressions.

There is a remaining migration-history case. V5 treats supersession as a historical fact: a live observation that once carried key K can suppress K even after that observation is updated to another key. V6 deletes the relation and rebuilds it from the live rows’ currently stored fields. An earlier key represented only by a historical supersession can disappear, allowing an old export copy to reappear. A retained tombstoned row with unchanged fields is handled; a historical key lost through an upsert is a different case. Preserve or explicitly reconcile that history before deleting the old relation. Your reported archive has no production live-phone stream, so this is not evidence that the rehearsal suffered that defect; it prevents unconditional acceptance of the migration across supported histories.

The 291 restored source records are not themselves a defect. Preserving distinct source elements is better than silently destroying their distinctions. The problem is the analytical contract: canonical_observations retains their multiplicity, while documentation recommends grouping by origin_key for strict totals. That key deliberately discards fractional seconds, rounds values, and omits distinguishing device/metadata fields. Consequently, blanket DISTINCT origin_key is not a universally valid logical-measurement deduplicator either. It can merge genuinely distinct observations that share those reduced inputs.

The remedy is to expose source-record multiplicity, resolved logical observations, and ambiguous equivalence groups separately. Preserve all source rows. For the reported 120 groups, record the justified duplicate resolution or report their unresolved contribution. Do not make every new ChatGPT conversation rediscover a footnote before producing a sum or weighted average. I cannot infer which metrics the 291 rows affect or how large their metric-specific impact is from the overall row count.

Swift/Python normalization: meaningful alignment, incomplete equivalence proof

The ordinary category/workout mismatch is improved. Both server ingestion and export import use the Python key function; Swift now emits explicitly mapped units, category strings, and workout strings. The Swift tests check representative XML forms and, where HealthKit is available, SDK constants and unit compatibility. Those are genuinely discriminating tests, not mere compilation evidence.

Whole-second keying is not automatically a bug. It addresses precision differences between the two producers. But the passing fractional-second example does not establish every boundary case, and reduced precision makes the key an equivalence heuristic rather than an identity proof.

Two concrete gaps remain. Python’s quantity normalization largely preserves the incoming unit, apart from its explicit alias mapping, while Swift converts requested quantities to selected units. An allowed export expressed in a different compatible unit can therefore fail to match the equivalent live quantity. Also, unknown workout raw values are mapped to HKWorkoutActivityTypeOther; a test positively asserts that fallback. “Unknown activity identifier” is not the same fact as the known “Other” category. Preserve the raw identifier and mark unsupported normalization rather than inventing that classification.

Before live sync is enabled, add an actual cross-language pipeline test: Swift-serialized payload → Python accept_batch → equivalence with the corresponding export element. Cover fractional boundary values, compatible-unit conversions, legacy category aliases, unknown activities, and multiple distinct samples sharing a whole second. These are live-sync activation blockers, not reasons to withhold a repaired export-only foreground release.

read_at: the string ordering is sound within its invariant; the evidence guarantee is narrower

The stored timestamps generated by utcnow() have a common UTC offset and fixed fractional precision. Lexicographic comparison is chronologically sound for those canonical strings. I would not reject _written_after merely because it compares strings.

The new worker guard also closes a real case: it rejects cited records or observations written after investigation start even when the model echoes no versions. The regression deliberately supplies empty version metadata and creates evidence during the investigation. That would fail if the guard were removed.

However, investigation-start wall time is not a database snapshot or a commit-order token. It still leaves these gaps:

Foreground analysis writes: context_capture/context_revise still pass evidence IDs without a trusted read token or expected versions; put_record stamps whatever versions are current at commit.

Derived pages: page references remain "immutable" although extraction can replace their text.

Query membership and normalization: newly added rows or changed canonical membership can change an aggregate without invalidating references to its old members.

Clock behavior: backward clock adjustment or identical timestamps do not provide a strictly increasing mutation order.

The first three affect foreground authority today. The timestamp safeguard in the disabled worker does not clear them.

The smallest robust implementation is a database-issued investigation/read token tied to a monotonic committed data generation, plus versioned derived-page content. Initially, rejecting any relevant generation change is acceptable and conservative. Later, dependencies can be narrowed to avoid unnecessary retries. Keep original-byte hashes immutable; do not apply that label to replaceable extraction text.
