2. CORE CORRECTNESS

2.1 Evidence binding: the sequence is sound; the dependency definition is not

Revising R2-14: replacing wall-clock ordering with a committed change-log sequence is the right correction. The implementation also versions extracted page text by its content hash, and re-extraction emits a change. Those improvements address the specific clock-ordering and “derived text is immutable” defects. The corresponding tests exercise changed observations and re-extracted pages.

R2-07/R2-08 are not cleared, however. _changed_since compares a changed batch’s window with the intervals of the cited observations. It does not know the aggregate’s requested window, predicate, source set, or canonicalization dependency.

A concrete counterexample is a daily mean initially computed from observation A at 09:00–09:10 with value 10. Observation B later arrives at 11:00–11:10 with value 30, inside the same requested day. The mean changes from 10 to 20, but B’s interval does not overlap A’s interval. _changed_since(..., [A], old_token) returns no stale references. My isolated execution produced exactly that result. The committed “new aggregate member” test uses an overlapping new sample, so it exercises a narrower property than its name suggests.

The same problem occurs when a non-cited aggregate member is deleted or moved outside the query window. Deleting a directly cited observation is detected through evidence existence/currentness; deleting another member is not necessarily detected. An aggregate with no rows is an especially clear case: there are no observation IDs from which to infer its dependency.

Supersession exposes another missing dependency. A live-source batch can change the canonical membership of an export-source row, but _changed_since requires the batch source to equal the cited row’s source. That cross-source case is an activation concern while live sync is excluded. The broader defect—depending on row intervals rather than the actual query—is already relevant to foreground backfill analysis.

There is also a post-commit gap. The token participates in the write check and receipt hash, but the persisted analysis dependencies remain reference versions. Later reads use _stale_refs, not a stored aggregate/query dependency. Consequently, an analysis that was valid when saved can continue to be returned as current after a new aggregate member changes its answer. Fixing only admission-time checking does not provide durable analytical memory.

Accepting captures without a token is appropriate for independent primary statements, but not for certifying derived evidence. “I ate dinner at seven” should not need a prior database read. In contrast, the compatibility path currently accepts an evidence-citing analysis without a token and stamps current versions onto it. That recreates the original failure rather than detecting it. The limitation is disclosed, but disclosure does not satisfy the foreground-authority contract.

Even a supplied token is not bound to the evidence read. The tests explicitly obtain a fresh token from SELECT 1 and use it with an older reference. There is also no upper-bound validation against the store’s current sequence in the write implementation. These observations do not require assuming a malicious user: omitted arguments, reusing the most recent tool token, or combining evidence from several reads are normal client mistakes the proposed safeguard should detect.

Smallest robust repair: require evidence-binding information for derived writes, preserve tokenless primary capture, and initially invalidate observation-derived analyses on any observation/canonical-generation change. Persist that dependency and check it on later reads. Return a read receipt associated with the actual retrieval, not a freely interchangeable sequence from an unrelated call. Selective source/metric/window invalidation can follow once actual query dependencies—including empty results and cross-source canonical effects—are represented.

2.2 Import gating: the final crash window is safe, but the read and ownership boundaries are not

Revising the specific final-retirement crash concern: for one owner running the same import configuration, a crash after the last retirement page but before completion leaves the durable marker present. Completion updates the run and removes its own marker in one transaction. Rerunning the matching import can therefore complete reconciliation before reopening reads. I do not identify that particular crash interval as an unsafe early-open path. The existing interruption test is useful, although it injects KeyboardInterrupt after a page rather than exercising this exact final interval or a hard process kill.

The query gate itself has a time-of-check/time-of-use race. query_readonly reads import_in_progress, then executes the requested query without an explicit read transaction spanning both statements. A writer can commit the marker and an import page between them. The cached gated value remains false, while the query sees the newer, overlapping state.

I reproduced that ordering with two SQLite connections: the marker check returned false, no explicit transaction remained active, an import transaction committed, and the subsequent query returned the newer rows. The fix is a read transaction covering the marker check and the data statement. In WAL mode, that makes both reads use the same snapshot; SQLite’s official isolation documentation describes precisely this guarantee.  SQLite

Bootstrap and status still expose observation-derived numbers during import. bootstrap() reads catalog counts and extrema directly. source_status() returns active counts before attaching a blocking notice, and these are not one shared snapshot with bootstrap’s catalog. The sources table is also outside OBSERVATION_TABLES, so a direct query can obtain its observation-derived freshness fields without the observation gate.

Not all such output must be prohibited. Source identifiers and operational progress are useful during maintenance. But numeric catalog/coverage fields should either come from a complete published generation or be withheld/explicitly represented as provisional operational counts, not ordinary evidence. One warning elsewhere in a compound response is weaker than the stated backend guarantee.

context_search should remain available. It searches records and extracted pages, not observation measurements. Its concern is returning saved observation-derived analyses with an unjustified evidence.current=true; that belongs to the evidence-dependency repair, not a blanket search shutdown. Independent notes, questions, and originals should continue working.

The marker does not actually serialize imports. A matching archive hash permits another run to replace the marker, even if the first process is still active. The marker also omits since, timezone, and parser/configuration identity.

A paused full import can therefore be “resumed” by a second process using the same archive but a much narrower --since. The second process can finish its subset and clear the marker while the first still has work outstanding. Different timezones create another mismatch between permitted takeover and actual request identity. Thus the assertion that nothing can change between retirement selection and deletion is not established.

Smallest repair: acquire an exclusive process-level import lock; retain a durable recovery marker containing the complete import signature; permit recovery only after obtaining that lock; and require exact-signature recovery or an explicit full reconciliation. Preserve the owner-qualified final deletion. Separately, make all analytical reads and gate decisions snapshot-consistent.

2.3 repeat_of: preservation improves, but maintenance and matching are incorrect

The raw/canonical split is a useful correction to the prior instruction to apply blanket DISTINCT origin_key. The new repeat test genuinely checks ordinary suppression, device distinction, and promotion after deletion of the representative.

The old group is not recomputed when an upsert changes origin_key. The upsert reads previous metric/unit/time fields, but not the previous origin key. It adds only the new key to touched. Suppose A represents group K1 and B has repeat_of=A. Updating A to K2 recomputes K2 only. B remains hidden in K1 while pointing to a representative that is no longer equivalent. My isolated execution left only A visible where both A and B should be canonical. Deleting A is covered; moving A is not.

Repair both old and new groups inside the same transaction, including old-key-to-null transitions. Treat any changed canonical membership as an analytical-generation change. A repeat_of update presently does not itself change the peer row’s updated_at, which is another reason reference-version checking alone is insufficient.

The matching predicate is broader than “only creation metadata differs.” Both _mark_repeats and the v8 SQL compare selected measurement columns and device JSON. They do not require equality of timezone or non-creation metadata. My isolated execution hid one of two rows differing in timezone and measurement-context metadata. This directly contradicts the stronger preservation claim in the migration comment and reported disposition—not necessarily the actual classification of every production row.

I cannot conclude that the reported 279 marks are all wrong, or that the other 12 should have been marked. They may differ in multiple fields. The required production check is a field-level comparison of each suppressed record with its representative, not agreement with a total repeat count.

Use an explicit repeat signature that preserves all relevant source distinctions and excludes only a documented set of creation/import bookkeeping fields. Share its implementation between migration and ingestion. Since production is already v8, repair existing marks in a new forward migration, not by editing _v8 and assuming it will rerun.

Revising R2-05: the changed v6 migration now carries historical supersessions through the export rows they previously suppressed, and the K1→K2 regression checks the identified case. That specific migration defect is repaired for databases traversing the corrected migration. It is not a reason to demand live-sync activation in this foreground round.

A separate, smaller importer issue remains: _recorded tests whether a profile value ever existed, not whether it is the active profile. After profile A→B→A, the last A can be skipped while B remains active. Repeated identical snapshots should be deduplicated; a return to an earlier state is still a new revision.

2.4 Manifest recursion: it follows producer names but ignores the consumed digest

Revising part of R2-11: declared-input validation, recursive checking, hashed repository test drivers, and the committed engineering runner are meaningful improvements. The new tests reject stale source trees, changed evidence without a matching producer, missing inputs, and cycles. The engineering manifest no longer depends on the private temporary driver identified in Round 2.

The central dependency binding remains broken. _inputs_valid reads the parent’s meta["manifest"], but never compares the parent’s recorded meta["sha256"] with the input file or producer evidence hash.

A normal rerun is enough to demonstrate the failure:

Summary S consumed input bytes A and records A’s digest.

The upstream campaign is rerun under the same source tree, overwriting its result file and manifest with bytes B.

S is not rerun.

The validator sees that B matches the newly overwritten upstream manifest and accepts S, ignoring that S consumed A.

My isolated execution returned true for that stale parent. No forged source hash, edited summary, or malicious operator was required. The existing “input changed” test changes only the file; it does not replace the upstream manifest as a normal rerun would.

Require equality among the parent’s consumed digest, the current input digest, and the producer’s recorded output digest. Prefer immutable/content-addressed producer manifests; otherwise record and check their digest too.

A second boundary remains: --input is optional, and the builder validates only declared dependencies. The committed summary declares both result files, which is good, but not the run_meta.json files the summarizer also reads. 5. IDEAL-vs-ACTUAL DIFFERENCE + SUPERIOR REALIZATIONS

First: simplify freshness before optimizing it. The selective overlap rule looks more precise but is not correct for arbitrary SQL. A persisted observation-generation dependency is a better initial implementation: conservative, easy to test, and sufficient for a single-user foreground system. Introduce narrower dependencies only when the actual query predicate and canonicalization inputs can be represented.

Second: separate import recovery from execution ownership. A durable marker says an archive is unfinished; it does not prove who may write it. An exclusive process lock plus a durable full-signature marker solves this without staging the entire archive or adding a distributed coordinator. Snapshot-consistent readers then see either a complete old state or an explicit maintenance refusal.

Third: make repeat resolution a rebuildable projection. Preserve raw source rows, define exactly what differences may be ignored, use one signature implementation, and recompute both affected groups. A forward repair should compare the production marks with that definition and invalidate dependent analytical generations. Do not tune the rule to reproduce the reported count of 279.

Fourth: bind evidence graph edges, not filenames. Every parent must identify the exact input digest and immutable producer it consumed. Required producer-specific dependencies prevent optional declarations from silently omitting material inputs. This is a small local provenance graph, not a request for a general build platform.

Fifth: keep exact-host security and improve enrollment. The correct usability improvement is controlled registration and retry, not widening a name heuristic. A new regional host can remain a disclosed first-use limitation while the rest of foreground use proceeds.

These changes preserve natural capture and one-interface operation. None requires asking the user to manage evidence tokens, classify routine notes manually, or operate a second dashboard.
